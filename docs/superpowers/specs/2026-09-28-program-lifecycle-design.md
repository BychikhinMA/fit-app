# Этап 1 roadmap: режим программы и факт тренировки — дизайн

Дата: 2026-09-28. Статус: решения приняты, рекомендуемые варианты выбраны
владельцем («выбери все рекомендуемые»). Отклонённые варианты —
`2026-09-28-program-lifecycle-alternatives.md`.

## Цель и граница с Этапом 3

Этап 1 собирает **факты**: когда программа была активна, в какие дни недели
идут тренировки, какие тренировки реально выполнены. Этап 3 (Прогресс) их
**интерпретирует**: цели и вехи, ввод показателей, шкала прогресса, сверка
ожидаемого с фактическим по правилам без ИИ.

Прогресс в Этапе 3 должен двигаться только за счёт выполненных тренировок, а
пауза — осознанный перерыв, не пропуск. Поэтому Этап 1 хранит историю
периодов и отметки выполнения, а не просто флаг «активна».

**Входит в Этап 1:**

1. Старт / пауза / возобновление / стоп программы с историей периодов.
2. Выбор дней недели для тренировок.
3. Отметка «Тренировка выполнена» и статусы в календаре (выполнено /
   пропущено / впереди).
4. Чистая функция-граница `getScheduleFacts`, которую будет использовать
   Этап 3.

**Не входит:** счётчики и проценты («5 из 6»), шкалы, веса/повторы по
упражнениям, цели, показатели тела — всё это Этап 3.

## 1. Жизненный цикл программы

### Состояния

| Состояние | Когда | Что видно |
|---|---|---|
| Не запущена | у программы нет периодов | Главная: карточка «Программа готова» + «Начать». Календарь: тренировок нет. Вкладка «Тренировки»: блок «Программа не запущена» + кнопка «Начать» |
| Запланирован старт | есть открытый период с `started_on` > сегодня | Главная: «Старт <дата>». Календарь: тренировки с даты старта |
| Активна | есть открытый период с `started_on` ≤ сегодня | как сейчас: «Сегодня», календарь с тренировками |
| На паузе | последний период закрыт с причиной `pause` | Главная: «Программа на паузе» + «Продолжить». Будущие тренировки не показываются |
| Остановлена | последний период закрыт с причиной `stop` | Главная: «Программа завершена» + «Начать заново» |

### Модель данных — новая таблица `program_periods` (миграция `0008`)

```sql
create table program_periods (
  id uuid primary key default gen_random_uuid(),
  program_id uuid not null references programs(id) on delete cascade,
  profile_id text not null references profiles(id) on delete cascade,
  started_on date not null,
  ended_on date,               -- null = период открыт
  end_reason text check (end_reason in ('pause', 'stop')),
  created_at timestamptz not null default now(),
  check ((ended_on is null) = (end_reason is null)),
  check (ended_on is null or ended_on >= started_on)
);
-- не больше одного открытого периода на программу
create unique index program_periods_one_open_idx
  on program_periods(program_id) where ended_on is null;
```

- Период покрывает даты `[started_on, ended_on)`: день `ended_on` уже **не**
  входит. Пауза, нажатая сегодня, прячет сегодняшнюю тренировку; «Продолжить»
  в тот же день открывает новый период с `started_on` = сегодня и возвращает её.
- RLS: тот же паттерн, что у `workout_day_exceptions` (`0007`) — политика
  `"anon full access"` для гостевых профилей без `owner_id` и
  `"owner full access"` через `private.profile_owner_id(profile_id)`.
- После применения — обязательная проверка кэша PostgREST
  (`NOTIFY pgrst, 'reload schema'` + REST-запрос к таблице с ответом `200`),
  как в `0007`.
- `profile_id` дублируется для RLS и выборки без join; `programs` при
  пересборке плана удаляются (`plan-stub.ts`), периоды уходят каскадом.
- Существующие программы Максима и Марии остаются **не запущенными**
  (миграция периодов не создаёт) — владелец проверит флоу «Начать» сам.

### Действия

- **Начать** (из «Не запущена», «Остановлена») — шторка: дата старта (по
  умолчанию сегодня, можно выбрать будущую; прошедшую нельзя) + выбор дней
  недели (раздел 2). Создаёт открытый период.
- **Пауза** (из «Активна») — закрывает открытый период: `ended_on` =
  сегодня, `end_reason = 'pause'`. Если старт ещё впереди — вместо паузы
  «Отменить старт» (удаляет открытый период).
- **Продолжить** (из «На паузе») — новый открытый период с `started_on` =
  сегодня.
- **Остановить** (из «Активна», «На паузе») — подтверждение внутри
  приложения (не `window.confirm`). Если период открыт — закрывает его с
  `end_reason = 'stop'`; если программа на паузе — меняет `end_reason`
  последнего периода на `stop`.
- **Начать заново** — то же, что «Начать»: новый период поверх истории,
  программа та же. Пересборка плана — по-прежнему через онбординг.

Где кнопки: «Начать» / «Продолжить» / «Начать заново» — на Главной и во
вкладке «Тренировки»; «Пауза» и «Остановить» — только в блоке «Программа» на
вкладке «Тренировки» (редкие действия, не на главном экране).

## 2. Дни недели

Отдельного хранилища нет: у каждого дня программы уже есть
`workout_days.weekday`. Выбор дней переставляет эти значения.

- Выбор — ряд из 7 чипов (Пн…Вс, переиспользуем `Chip`). Нужно выбрать ровно
  столько дней, сколько дней в программе (N); кнопка сохранения неактивна,
  пока выбрано не N, подпись «Выбери N дня/дней».
- Дни программы раскладываются по выбранным дням недели по возрастанию, в
  порядке `sort_order` (День 1 → первый выбранный день и т.д.).
- Предвыбор по умолчанию — равномерный разнос: 2 → Пн, Чт; 3 → Пн, Ср, Пт;
  4 → Пн, Вт, Чт, Пт; 5 → Пн, Вт, Ср, Пт, Сб; 6 → Пн–Сб. `plan-stub.ts` тоже
  раскладывает новые дни по этому разносу (сейчас — подряд с Пн).
- Где: в шторке «Начать» и отдельно «Изменить дни» в блоке «Программа» на
  вкладке «Тренировки» (доступно в любом состоянии).
- При сохранении новых дней удаляются **будущие** исключения переноса
  (`workout_day_exceptions.date >= сегодня`) — иначе старые разовые переносы
  и отмены легли бы на новую раскладку. Шторка предупреждает об этом, если
  такие исключения есть. Прошлые исключения не трогаем. Постоянные переносы
  перезаписываются новой раскладкой — это ожидаемо.

## 3. Показ тренировок и отметка «выполнено»

### Какая тренировка на дату

Новая чистая функция поверх существующей:

```ts
// null, если дата вне активных периодов; иначе — findWorkoutForDate(...)
workoutForDate(workoutDays, date, exceptions, periods)
```

Все места, где сейчас вызывается `findWorkoutForDate` для показа (5 видов
календаря, `month-mini`, Главная, выбор даты в шторке переноса,
`isScheduledOnOrigin` на экране тренировки), переходят на неё. Прошлые
периоды остаются видны (история), паузы и время до старта — пустые.
Кнопка «Перенести» автоматически пропадает на паузе, потому что
`isScheduledOnOrigin` станет ложным.

### Отметка

- На экране тренировки кнопка «Отметить выполненной», если: день стоит на
  `originDate` (через `workoutForDate`) и `originDate` ≤ сегодня. Будущее
  отметить нельзя; прошлое — можно (забыл отметить вовремя).
- Нажатие — вставка в существующую `workout_logs`: `profile_id`,
  `workout_day_id`, `date = originDate`, `day_label`, `context_used`
  (активный контекст экрана), `completed = true`.
- Отмеченная тренировка показывает «Выполнено ✓» и «Снять отметку»
  (удаляет запись).
- Миграция `0008` добавляет в `workout_logs` уникальный индекс
  `(profile_id, date, workout_day_id)` — таблица сейчас пуста, индекс
  безопасен; повторное нажатие не создаёт дубль.

### Статусы в календаре

| Статус | Условие | Вид |
|---|---|---|
| Выполнено | есть запись `workout_logs` на дату | галочка вместо точки |
| Пропущено | дата < сегодня, в активном периоде, тренировка запланирована, записи нет | приглушённая точка/подпись «пропущено» |
| Впереди | дата ≥ сегодня, запланирована | точка, как сейчас |

Статусы — в видах День / Неделя / Месяц и на карточке «Сегодня» на Главной.
Квартал / Год оставляем с точками (только учитывают периоды) — слишком мелко
для трёх статусов.

## 4. Граница для Этапа 3

```ts
type DayFact = {
  date: string;              // YYYY-MM-DD
  status: 'done' | 'missed' | 'planned' | 'paused' | 'not_started';
  workoutDayId: string | null;
};
getScheduleFacts(plan: PlanData, from: Date, to: Date, today: Date): DayFact[]
```

- `paused` — дата внутри паузы (между закрытием с `pause` и следующим
  стартом), `not_started` — до первого старта или после стопа.
- Дни отдыха в активном периоде в результат не попадают.
- Чистая функция, без обращений к базе; Этап 3 использует только её.

## 5. Код и загрузка данных

- `loadPlan` (`src/lib/load-plan.ts`) дополнительно грузит периоды активной
  программы и все `workout_logs` профиля в `PlanData`
  (`periods`, `workoutLogs`). Объём данных маленький — без пагинации.
- Чистая логика (состояние программы, `workoutForDate`, раскладка дней,
  `getScheduleFacts`) — новый модуль `src/lib/program-schedule.ts` без
  `@/`-импортов, чтобы его покрывал `npm test` (`node:test`); как именно
  подключить его к тестам при импорте из `calendar-dates.ts` — решается в
  плане.
- Мутации (start/pause/resume/stop/cancelStart, setWeekdays, markDone/unmark)
  — `src/lib/program-lifecycle.ts`, по образцу `reschedule.ts`; ошибки —
  через `errorMessage`.
- Типы — руками в `src/types/database.ts` (`program_periods`, как сейчас
  принято).
- `plan-stub.ts`: равномерный разнос дней; периоды не создаёт (новая
  программа — «Не запущена»).

## Открытые риски

- Перенос «разово» на дату внутри паузы технически возможен только если
  исходная дата активна; целевая дата в паузе не покажется. Выбор даты в
  шторке переноса будет показывать даты паузы без точек — отдельного запрета
  не делаем, это хвост Этапа 0b.
- Смена дней стирает будущие исключения — осознанное упрощение, пользователь
  предупреждается.
