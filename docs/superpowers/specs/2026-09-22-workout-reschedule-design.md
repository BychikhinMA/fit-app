# Дизайн: перенос тренировки на другую дату

Создано 2026-09-22. Обсуждено и утверждено пользователем в этой сессии
(brainstorming, architectural path). Здесь — технический дизайн перед
написанием плана реализации (writing-plans). Код пока не тронут.

## Цель

Сейчас (Calendar v2, коммит `05b3af1`) расписание тренировок целиком
вычисляется на лету из `workout_days.weekday` (`src/lib/calendar-dates.ts`,
`findWorkoutForDate`) — программа считается бессрочной и еженедельно
повторяющейся, ни одна конкретная календарная дата в БД не хранится.

Нужна возможность «перенести» тренировку с одной даты на другую:
- разово (только эта конкретная дата, на следующей неделе всё возвращается
  на исходный день недели) — выбор пользователя,
- либо навсегда (меняется сам `weekday` тренировки в программе) — тоже
  выбор пользователя, явно на каждый перенос.

## Отличия от того, как сформулировал вопрос пользователь

Пользователь в исходном вопросе предлагал таблицу вида
`workout_day_overrides`/`workout_instance_moves` с полями
`workout_day_id`/`original_date`/`new_date`. Вместо одной «move»-записи на
две даты сразу предлагается таблица **исключений** с одной строкой на одну
дату (`workout_day_exceptions`, см. ниже) — по одной записи `cancelled` на
исходную дату и `scheduled` на целевую. Это не одна семантическая сущность
«перенос», а два примитива, которые перенос **использует**, но которые
композируются с другими случаями без специального кода:
- конфликт на целевой дате разруливается симметрично (своп — это просто
  ещё одна `scheduled`-запись, без нового типа объекта),
- «отменить тренировку без переноса» и «добавить внеплановую тренировку»
  becomes free (не реализуются в этом шаге — см. «Не входит в объём»), но
  не потребуют новой миграции в будущем.

Постоянный перенос (`weekday` меняется навсегда) вообще не требует новой
таблицы — это прямой `UPDATE workout_days SET weekday = ...` поверх
существующей колонки из `0006_workout_day_weekday.sql`.

## Модель данных

### Разовый перенос — новая таблица `workout_day_exceptions`

Одна строка = одно исключение из недельной сетки на конкретную дату:

| Колонка          | Тип         | Примечание                                          |
|-------------------|-------------|------------------------------------------------------|
| `id`               | `uuid`      | PK, `gen_random_uuid()`                              |
| `profile_id`       | `text`      | `references profiles(id) on delete cascade`, прямая ссылка (как у `training_contexts`, не через security-definer цепочку) |
| `date`             | `date`      | конкретная календарная дата                          |
| `kind`             | `text`      | `check (kind in ('scheduled', 'cancelled'))`          |
| `workout_day_id`   | `uuid`      | `references workout_days(id) on delete cascade`, **null** при `kind = 'cancelled'`, **обязателен** при `kind = 'scheduled'` |
| `created_at`       | `timestamptz` | `default now()`                                    |

Ограничения:
- `check ((kind = 'scheduled' and workout_day_id is not null) or (kind = 'cancelled' and workout_day_id is null))`
- `unique (profile_id, date)` — на одну дату не больше одного исключения
- индекс `(profile_id, date)`

`kind = 'scheduled'` — в эту дату показываем `workout_day_id`, даже если по
`weekday` там должно быть другое/ничего.
`kind = 'cancelled'` — в эту дату не показываем ничего, даже если по
`weekday` должна быть тренировка.

Разовый перенос дня X с даты A на дату B = две строки:
`{date: A, kind: 'cancelled'}` + `{date: B, kind: 'scheduled', workout_day_id: X}`.

### Постоянный перенос — без новой таблицы

`UPDATE workout_days SET weekday = <weekday целевой даты> WHERE id = ...`.
Существующая колонка, existующий механизм (`findWorkoutForDate` уже читает
`weekday`), никаких новых сущностей.

### Изменение `findWorkoutForDate` (`src/lib/calendar-dates.ts`)

Сигнатура расширяется: функция должна сначала посмотреть, есть ли
исключение на точную дату (`exceptions.find(e => isSameDay(e.date, date))`):
- если есть и `kind = 'scheduled'` — вернуть соответствующий `workout_day`
  из уже загруженного списка (по `workout_day_id`),
- если есть и `kind = 'cancelled'` — вернуть `undefined` (как «тренировки
  нет»),
- если исключения нет — текущая логика по `weekday`, без изменений.

`PlanData` (`src/lib/load-plan.ts`) получает новое поле `exceptions:
WorkoutDayException[]`, загружается там же, где остальные сущности плана
(`loadPlan` — один запрос `select('*').eq('profile_id', profileId)`, объём
данных для семейного приложения мал, разбивать по диапазону дат не нужно).

### Регенерация плана — обязательная правка (по замечанию пользователя)

`src/lib/plan-stub.ts`, рядом с существующим
`await supabase.from('programs').delete().eq('profile_id', profileId);`
(строка ~134) — добавить
`await supabase.from('workout_day_exceptions').delete().eq('profile_id', profileId);`.

Без этого старые `cancelled`-исключения переживут пересборку плана и будут
молча гасить тренировки в новом плане на тех же датах (у нового плана
могут быть совершенно другие `workout_day_id`, но `date`/`kind='cancelled'`
всё равно совпадёт и «съест» тренировку). Порядок относительно других
`.delete()` в `generateStubPlan` не важен — таблица ни от чего не зависит
внешними ключами кроме `profiles`/`workout_days`, а `workout_days` в этот
момент ещё не пересоздан, так что удаление исключений можно делать в любой
точке до конца функции; логичнее всего рядом с `programs.delete()`.

### Прошлые логи не страдают

`workout_logs` уже хранит собственные `date`/`workout_day_id`/`day_label`
на момент записи (снапшот, не производная величина) — перенос дня в
будущем/прошлом не переписывает и не портит уже сделанные записи логов.

## Миграция (текстом, для ручного применения в Dashboard → SQL Editor)

`supabase/migrations/0007_workout_day_exceptions.sql`:

1. `create table if not exists workout_day_exceptions (...)` — колонки и
   ограничения как в разделе «Модель данных» выше.
2. Индекс `create index if not exists workout_day_exceptions_profile_date_idx on workout_day_exceptions(profile_id, date);`
3. `alter table workout_day_exceptions enable row level security;`
4. Две RLS-политики, тем же паттерном, что уже есть у `training_contexts`
   (прямой `profile_id`, без новой security-definer функции):
   - `"anon full access"` — для гостевых профилей без `owner_id`
     (`profile_id in (select id from profiles where owner_id is null)`)
   - `"owner full access"` — для роли `authenticated`, через
     `profile_id in (select id from profiles where owner_id = auth.uid())`

**Обязательный пост-шаг после применения миграции (по замечанию
пользователя, из-за уже случавшегося `PGRST205` на `profile_settings` в
этой же сессии):**

1. Сразу после `create table`/RLS — выполнить в том же SQL Editor:
   `NOTIFY pgrst, 'reload schema';`
2. Проверить наличие таблицы в **Dashboard → Project Settings → API →
   Exposed schemas** — `public` должен быть в списке (то, из-за чего
   заподозрили `profile_settings`).
3. Сделать прямой REST-запрос к новой таблице (например
   `GET {SUPABASE_URL}/rest/v1/workout_day_exceptions?limit=1` с anon-
   ключом в заголовке) и убедиться, что ответ **200**, а не `PGRST205`
   (`Could not find the table 'public.workout_day_exceptions' in the
   schema cache`).
4. Если после `NOTIFY` всё ещё `PGRST205` — тот же крайний вариант, что
   обсуждали для `profile_settings`: **Restart project** в Dashboard
   (предупредить пользователя перед этим шагом, это временная недоступность
   API).

Это часть плана реализации (не брейнстроминга) — фиксирую здесь, чтобы шаг
не потерялся при переходе в writing-plans.

`src/types/database.ts` — вручную добавить типы `workout_day_exceptions`
(Row/Insert/Update), синхронно с остальными таблицами (миграции применяются
вручную, автогенерации типов нет — см. текущее состояние проекта в
CLAUDE.md).

## UI/UX

### Точка входа — одна, на `workout-day/[id].tsx`

Новая кнопка «Перенести» на экране дня тренировки (рядом с уже
существующим переключателем контекста и `back-button`). Так все масштабы
календаря получают перенос «бесплатно», без дублирования UI 5 раз: День /
Неделя / Месяц уже ведут на этот экран по тапу на день (текущее поведение
не меняется); Квартал/Год — только через Месяц, как и сейчас (там даже
отдельный день не кликабелен, кликабелен весь мини-месяц — сознательное
решение из Calendar v2, не меняется).

Флоу:
1. Тап «Перенести» → модалка с мини-календарём (переиспользуем
   `month-mini.tsx`) для выбора целевой даты.
2. После выбора даты → шторка с двумя вариантами: «Только в этот раз» /
   «Теперь всегда» (пользователь выбирает каждый раз, без запоминания
   выбора).
3. Если на целевой дате уже что-то есть (по `weekday` или по другому
   исключению) — диалог конфликта: «На {дата} уже стоит {день}. Поменять
   местами? / Отменить перенос?». Своп = ещё одна `scheduled`-запись (или,
   при «навсегда», два `weekday`-апдейта), без `cancelled`-записей — обе
   даты продолжают что-то показывать, просто местами.

### Drag-n-drop — только `week-view.tsx`, только внутри одной недели

Long-press на карточке дня → перетаскивание на другую ячейку **той же
видимой недели**. Кросс-недельный drag сознательно не делается — требует
автоскролла во время жеста, отдельная и рискованная a11y/UX история; для
переноса на другую неделю всегда есть кнопочный флоу. Drop запускает ту же
логику (разово/навсегда + проверка конфликта), что и кнопочный флоу — один
код мутаций, два входа в него.

Кнопочный флоу обязателен как основной для VoiceOver/TalkBack — drag-n-drop
недоступен без него, а этот флоу и так покрывает 100% случаев (включая
кросс-недельные), drag — просто ускоритель для соседних дней внутри недели.

## Крайние случаи

- **Конфликт на целевой дате** — не перезаписываем молча, всегда диалог
  (см. UI/UX выше).
- **Контекст (дом/зал)** — не трогаем вообще. `workout_days.default_context`
  и `exercises.context_variants` остаются как есть, переключатель контекста
  на `workout-day/[id]` продолжает работать вручную независимо от переноса.
  Не пытаемся угадывать контекст по дню недели/дате.
- **Возврат на следующей неделе** — решено: пользователь выбирает каждый
  раз (разово через `workout_day_exceptions`, навсегда — прямой `UPDATE
  weekday`), никакого запоминания предпочтения.
- **Регенерация плана** — старые исключения профиля удаляются вместе с
  остальным планом (см. правку в `plan-stub.ts` выше).
- **Прошлые `workout_logs`** — не зависят от `workout_days`/`weekday`
  напрямую (собственный снапшот `date`/`day_label`), перенос их не портит.

## Не входит в объём (сознательно, YAGNI)

- Голая отмена тренировки без переноса (`cancelled` без `scheduled`-пары) —
  модель данных это уже поддерживает бесплатно, но отдельного UI-входа в
  этом шаге не делаем, пользователь не просил.
- Добавление внеплановой тренировки на день без своей (`scheduled` без
  `cancelled`-пары) — аналогично, данные готовы, UI — нет.
- Кросс-недельный drag-n-drop.
- Запоминание выбора «разово/навсегда» между переносами.
